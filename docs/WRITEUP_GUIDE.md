# 롸잇업 · 힌트 작성법

`docs/write-ups/` 아래의 모든 롸잇업과, 각 CTF 폴더의 `HINT.md`가 따르는 규칙입니다.
목적은 하나입니다. **나중에 다시 봤을 때 "왜 그렇게 판단했는지"가 남아 있을 것.**

---

## 1. 단위와 위치

실습 단위는 **폴더명**입니다. 폴더명이 곧 CTF 이름이고, 그 안에 기록이 모입니다.

```text
docs/write-ups/red/<ctf-name>/
├── README.md      # 롸잇업 본문 (관찰 → 판단 → 실행 → 결과)
└── HINT.md        # 힌트 (근거 → 가설 → 확인 → 우회)
```

- 폴더명은 소문자-하이픈을 기본으로 합니다. (`attacktive-directory`, `hydra-base`)
- 루트에 따로 관리 중인 실습 폴더도 같은 규칙을 따릅니다. (예: `Squid/README.md`, `Squid/HINT.md`)
- 문서가 방대하면 `<ctf-name>/1.md`, `2.md` … 로 쪼개고 `README.md`를 인덱스로 씁니다. (`cve-2026-22200` 참고)
- 스크립트·캡처는 `<ctf-name>/tmp/` 에 두고 본문에서 상대경로로 링크합니다.

---

## 2. 롸잇업 기본 원칙

- **관찰 → 판단 → 실행 → 결과** 순서로 씁니다.
- **장황하게 쓰지 않습니다.** 같은 말 반복, 배경 설명, 정리 안 된 생각은 넣지 않습니다.
- 각 단계는 1~3문장. 설명이 길어지면 그건 별도 문서로 빼야 한다는 신호입니다.
- 한 절에는 한 가지 주장만. 길어지면 덜어내고, 부연은 링크로 뺍니다.
- 명령은 **복붙 가능한 형태**로, 출력은 **판단에 쓴 줄만** 남깁니다.
- 실제로 친 명령과 실제 출력만 씁니다. 예상 결과를 실제 결과처럼 쓰지 않습니다.
- 민감 정보는 `REDACTED` 처리합니다. (패스워드, 개인키, 세션 토큰, 플래그)
- 표는 **비교·판정 기준**에만 씁니다. 그 외는 목록으로 풀어 씁니다.

---

## 3. 힌트 문서(`HINT.md`) 작성 규칙

힌트는 사실상 **롸잇업의 축약본**입니다. 그래서 같은 원칙 위에 아래를 더합니다.

- **토폴로지는 무조건 넣습니다.** 공격자 위치, 경유 지점, 대상 포트를 텍스트 다이어그램 한 블록으로.
- **힌트는 장황하게 적지 않습니다. 분량 상한은 100줄.**
- 남길 것은 네 가지뿐입니다: **3줄 요약 → README 근거(줄번호) → 확인 명령 → 경로(A/B/C)**.
- 표·예시·대안은 판정에 필요한 것만. "혹시 몰라서" 넣은 내용은 뺍니다.

### 3-1. `README.md`가 1차 근거다

- 힌트의 모든 주장은 **그 폴더 `README.md`에 기록된 실제 로그**에서 출발합니다.
- 근거를 댈 때는 **줄번호까지** 적습니다. → `README.md:235`
- README에 없는 사실을 쓰려면, 먼저 README에 그 관찰을 추가하고 힌트에서 인용합니다.
  (힌트가 README보다 앞서 나가면, 다음에 볼 때 근거를 못 찾습니다.)

### 3-2. 사실 / 추론 / 확정을 구분한다

| 구분 | 쓰는 법                                             |
| ---- | --------------------------------------------------- |
| 사실 | 로그를 그대로 인용. `README.md:235`                 |
| 추론 | "…라고 본다" + **왜 그렇게 봤는지** + **확인 명령** |
| 확정 | 확인 명령의 실제 출력을 붙임                        |

추론을 확정처럼 쓰지 않습니다. 반대로, 확정할 수 있는데 추론으로 남겨두지도 않습니다.

### 3-3. "왜 안 되는지"를 먼저, "어떻게 되는지"를 다음에

- 실패한 시도는 **지우지 않고** 왜 실패했는지 남깁니다. 그게 제일 값진 부분입니다.
- 안 되는 것 목록을 따로 모아 "시간 낭비 방지" 절로 만듭니다.
- 되는 방법은 하나만 추천하고, 대안은 "이럴 때" 조건과 함께 둡니다.

### 3-4. 도구는 "말투"까지 설명한다

- 명령만 던지면 다음에 같은 상황에서 또 막힙니다.
- "이 도구는 A 방식을 쓰고, 저 도구는 B 방식을 쓴다" 수준까지 한 줄로 적습니다.
  예: `proxychains`·`HYDRA_PROXY` = CONNECT(터널) / `curl -x`·`ffuf -x` = absolute-URI(포워드)
- 옵션은 **왜 그 옵션인지** 한 줄. (`-V`는 로그 폭발, `-t`는 프록시에서 과하면 전멸 등)

### 3-5. 재현 가능한 최소 단위로

- 확인용 명령은 5분 안에 끝나는 것으로 먼저 배치합니다.
- 전수 탐색처럼 오래 걸리는 작업은 **예상 소요 시간**을 계산해서 적습니다. (시도 수 ÷ 처리량)
- 중단·재개 방법(`hydra.restore`, `-od` 디렉터리)도 함께 적습니다.

### 3-6. 문서 골격

```markdown
# HINT — <한 줄 주제>

> 이 문서는 `README.md`의 실제 로그를 근거로 씁니다.
> 각 주장 옆의 `README.md:줄번호` 는 그 결론의 출처입니다.

## 0. 3줄 요약

## 1. 토폴로지 (필수)

## 2. 원리 (왜 이런 일이 생기는가)

## 3. README 로그에서 읽어낸 증거 (줄번호 인용)

## 4. 5분 진단 (가설 확인 명령)

## 5. 경로 A / B / C (조건별)

## 6. 함정 정리 (안 되는 것 + 이유)

## 7. 체크리스트
```

### 3-7. 좋은 예 / 나쁜 예

```markdown
# 좋은 예 — 근거가 붙어 있음

`README.md:235` 의 에러 페이지에 `ClientIP: 192.168.45.248` /
`ServerIP: 192.168.199.189` 가 함께 찍혀 있습니다. 둘이 다르다는 건
TCP 연결을 만든 주체가 내 kali가 아니라 **Squid**라는 뜻입니다.
→ `127.0.0.1` 은 Squid 기준으로 자기 자신입니다.

# 나쁜 예 — 결론만 있음

프록시가 127.0.0.1을 자기 자신으로 해석하니까 그렇게 하면 됩니다.
```

---

## 4. 마무리 체크리스트

- [ ] 폴더명이 CTF 이름과 일치하는가
- [ ] 토폴로지(공격자·경유·대상 포트)가 들어 있는가
- [ ] `README.md`에 관찰 로그가 먼저 기록되어 있는가
- [ ] 힌트의 모든 주장에 `README.md:줄번호` 근거가 있는가
- [ ] 추론과 확정이 구분되어 있는가
- [ ] 가설마다 확인 명령이 붙어 있는가
- [ ] 실패한 시도와 그 이유가 남아 있는가
- [ ] 오래 걸리는 작업에 예상 소요 시간이 적혀 있는가
- [ ] 패스워드·토큰·플래그가 `REDACTED` 처리되었는가
